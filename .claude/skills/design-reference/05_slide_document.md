# スライド・文書(プレゼン/マニュアル)の型

作成日: 2026-09-13。根拠は `slide_design_standard.md` / `document_design_standard.md`(拠点共通基準、
`/home/shiromae/dev/sandbox/portfolio-sites/docs/`)と、基準作(サウナご利用ガイド)と低評価作(サウナ/あざらしの
プレゼン・マニュアル)を実測比較したブラッシュアップ設計書(2026-09-13、殿評価「めちゃくちゃよかった」作を
基準に採用)。この節は上記 2 基準に矛盾しない範囲の追記であり、頁の作り方・レイアウト型そのものは変えない。
低評価の原因は「箇条書き・表中心という構成」ではなく、**書体が単調・色面がベタ塗り・図版が少ないこと**だった。

## 1. 基準作の型(サウナご利用ガイド、実測)

対象: `penguin-sauna-manual`(20 頁、殿評価「めちゃくちゃよかった」)。ソースは `assets/css/common.css` と
実頁の直接確認(申告の転記ではない)。

- **二書体構成**: 本文は `Noto Sans JP` のみ。見出し(h1/h2/h3)・章のゴースト数字・小ラベル(eyebrow・
  step-title・toc-num・頁番号)だけ `Zen Maru Gothic`(丸ゴ)。**丸ゴは短い語・数字に限定し、長文には使わない**。
- **5 色構成**: `--deep-green:#2F4F3E`(見出し・章扉背景・アイコン円)/ `--brown:#4A362A`(章扉第 2 色・
  キャプション)/ `--pale-blue:#DCEFF2`(info pill・カード背景)/ `--text:#2B2B2B` / `--muted:#6b6b6b`
  (+罫線 `--rule:#d7e4e2`)。章ごとに deep-green と brown を使い分けるだけで、**案件ごとに色を増やさない**。
- **アイコン**: 線画+単色塗り円、直径 44px 相当・内側アイコン 24px で全頁統一。漢字 1 字などの略号を
  アイコン代わりにした箇所は無い。
- **図版占有率 40〜60%**(document_design_standard.md の基準と同値)。20 頁中、図版ゼロの頁は無い。
  表主体の頁(料金表)も下段に 3 カードを足して図版比率を確保している。
- **章扉の型**: 色面 100%(deep-green か brown)+右下に巨大ゴースト数字(丸ゴ)+左下に円アイコン+章題。
- **info pill + 3 カードの型**: 見出し(小ラベル+H1+下線バー 4px)→本文→info pill 行(アイコン+短文を
  角丸カプセルに 3 個並べる)→3 カードグリッド(アイコン円+太字見出し+3 行説明、カード背景は淡色塗り・
  枠線なし)。番号は「大きな数字+短い動作+アイコン」のセットで出し、単独の丸数字だけを置く頁は無い。
- 数値基準の再掲(document_design_standard.md と一致): 本文 10.5〜12pt、見出し 18〜24pt、
  キャプション 8〜9pt、注意/ヒント/確認ボックスは 1 章に 1 つ以上。

## 2. 案件の世界観の持ち込み方(LP から書体・色・角丸・帯を写す)

殿方針(2026-09-13): プレゼン・マニュアルには「LP 3 本の世界観」(書体・カード・帯・大きな写真)を持ち込む。
独自に近似色・近似書体を作らず、**LP の実装値をそのままコピーする**。

1. 同一案件の LP の `brand.json` / `:root` の CSS 変数を開く。
2. 色トークンをそのままコピーする(deck 側・manual 側が別のトークン名で持っている場合は値を合わせる)。
3. 見出し書体・本文書体・数字書体を LP の `font-family` 宣言から拾う。
4. `border-radius` の値を LP のボタン・カードから拾う(角丸小さめの案件、ピル型ボタンの案件をそのまま踏襲する。
   独自の角丸値を決めない)。
5. 帯(セクション区切りの色面、写真の上の半透明オーバーレイ)の使い方を LP のセクション背景から真似る。
6. ブランドトークンは 1 つのソース(`brand.json` / `common.py` 等)に集約し、LP・デック・マニュアルで共有する。

実例(あざらし、design書 D-2): LP が `--ink:#132430; --accent:#0a9cc0; --head:'Kaisei Opti'; --eng:'Montserrat';
--mono:'IBM Plex Mono'` を使っているのに、デックの `common.py` は別の青(`#1467B4`)+ゴシック単一書体を
使っていたため「同じ製品なのに別会社の資料に見える」状態になっていた。LP の値へ置き換えて解消する。

LP が無い/薄い案件(氷原の湯サウナ)は、既存の最高評価作(ガイド)をブランド基準にして、そこから書体・色を
強化する(1 節の型をそのまま強化する。新規のブランド決定はしない)。

## 3. 書体の組み方(4 役、OFL 限定)

> **但し書き(2026-09-13 GM 裁定 #178)**: 案件の基準作や LP が二書体構成(見出し・数字・ラベル=1 書体、本文=1 書体。例: 氷原の湯ガイドの Zen Maru Gothic+Noto Sans JP)なら、数字も英数字専用書体にせず**その構成に従う**。4 役は LP が 4 役(例: あざらしの Kaisei Opti / Montserrat / IBM Plex Mono / Noto)のときに使う。案件内で書体構成を揃えることを優先する。

書体は用途で 4 役に分ける。1 案件で 2〜4 書体になってよいが、役をまたいで使い回さない。

| 役 | 使うもの | 例(あざらし案) |
|---|---|---|
| 見出し・章題・ゴースト数字 | 案件の世界観書体(丸ゴ/明朝など、LP から) | Kaisei Opti |
| 本文 | 可読性優先の和文書体 | Noto Sans JP |
| 数字・KPI・図番・頁番号 | 英数字専用書体(和文書体のまま数字を打たない) | Montserrat |
| ラベル・キャプション・図版内の短い注記 | 等幅系など LP のログ・データ表現に使う書体 | IBM Plex Mono |

- **丸ゴシック(Zen Maru Gothic 等)は見出し・短い語・数字にだけ使う**。本文・長文に丸ゴを当てない
  (1 節のガイドの使い分けをそのまま踏襲)。
- **丸バッジ禁止**: 概念・章タイトルを漢字 1 字などに略号化して円の中に置くバッジは作らない(かわいい方向に
  転び、実在の SaaS マニュアル・IR 資料のトーンから外れる)。代わりに「角の立った正方形バッジ+ゴシック太字の
  数字」または「帯(色面)+フルタイトル」を使う。手順の丸数字(①②③相当)も同様に、直径指定の円形バッジでは
  なく**角丸 4px 程度の正方形バッジ**に統一する(色・文字色は変えず形だけ変える)。
- **書体は OFL(SIL Open Font License、Google Fonts 配布分)限定**。理由: PPTX へのフォント埋め込みは
  配布(埋め込み)許可が要るため、デスクトップ利用限定の Morisawa Fonts(SKILL.md 5 節)はスライド/文書の
  埋め込みには使わない。Web デザインカンプ・動画焼き込みなど埋め込みを伴わない用途では Morisawa の指定を
  そのまま使ってよい。
- 使用ウェイトのみサブセット埋め込みにする(全ウェイト埋め込みはファイル肥大化を招く)。和文 run には
  `<a:ea>`、英数字 run には `<a:latin>` を分けて指定する(`slide_design_standard.md` の既存規則どおり)。
- 検品は PowerPoint COM 実機レンダ(`powerpoint-com-render`)で「意図した書体が実際に当たっているか」を
  確認する。埋め込みが効いていない場合は代替書体(Noto Sans JP 等)で描画されるため、検品ですぐ判る。

## 4. 図版の調達(この順で確認する)

1. **既存アセットの流用**: 依頼を受けたら、まず同一案件の他成果物(LP・サイト・別デック)に使える写真・
   スクリーンショット・アイコンが無いか確認する。`sha256sum` での完全一致確認、または `assets/` 配下の
   ファイル一覧 grep で「同じ画像がすでにある」ことを裏取りしてから使う(申告の「たぶん同じ」を転記しない)。
2. **クルーの線画自作**: 流用できるものが無い場合、線画アイコン(SVG、単色、直径 40〜48px 相当)・図解・
   インフォグラフィックはクルーが自作する。注意/ヒント/確認ボックスの小アイコン(三角に!/電球/チェック)は
   3 種作れば全頁で使い回せる。
3. **殿への画像生成依頼**: 1・2 で埋まらない場合だけ、実写風写真・人物が写るエディトリアルイラストを
   画像生成依頼書へ回す。依頼書には使用 AI モデル名を明記する(SKILL.md 6 節の既存ルールと同じ)。

線引き: **線画アイコン・図解・インフォグラフィックはクルー、実写風写真・人物が写るイラストは殿**。
実例: サウナ・あざらしのブラッシュアップはいずれも新規画像生成 0 枚(1・2 の流用と自作だけ)で解決できた。

## 5. 面の質感(ベタ塗りを減らす)

- 単色の四角パネルだけで画面の大部分を構成しない。写真の上に半透明の色帯(白かブランド色、不透明度
  30〜50% 程度)を敷いて見出し・キャプションを乗せる(文字の可読性は保ちつつ、色面ベタ塗りより質感が出る)。
- セクションの区切りは太い枠線・影ではなく、細い罫線(1px、`--rule` 相当のグレー系)で行う。
- カード間・行間に余白を作る。図版占有率(40〜60%)は満たしていても、余白ゼロで詰め込むと単調に見える。
- グラフはツールの既定色(細いグリッド線・既定フォントの軸ラベル)のまま出さず、ブランド色 2 色+グレーに
  統一し、棒グラフの角を軽く丸める(matplotlib なら `patches` の corner rounding)。
- グラデーションは章扉・締め頁などの装飾に限定し、本文頁・表・グラフの本体には使わない
  (データ表現にグラデーションを使うと数値が読み取りにくくなるため)。

## 6. 検品の見方(見た目の合格線チェックリスト、技術検品とは別に見る)

技術検品(フォント埋め込み・座標超過・和文 run の ea 指定など、`slide_design_standard.md` の「PPTX 出力の
技術要件」)を通過した後、次の 10 項目を現物(実ファイル・実レンダ)で数える。1 つでも該当すれば差し戻す。

1. 見出し書体と本文書体が同一になっている頁が無いか。
2. 概念・章タイトルを 1 文字略号+丸バッジにしている箇所が無いか。
3. 図版が頁の 40〜60% を占めていない頁(図版ゼロを含む)が無いか。
4. 同一案件の LP・デック・マニュアルで配色トークンが食い違っていないか(値を突合する)。
5. KPI・図番・頁番号などの数字が和文書体のまま打たれていないか(英数字専用書体になっているか)。
6. 単色パネルだけで構成され、写真・線画・帯のいずれも乗っていない頁が無いか。
7. アイコンの線幅・塗り(線画+単色円、直径 40〜48px 相当)が頁ごとにばらついていないか。
8. グラフがツールの既定色・既定グリッドのままになっていないか。
9. OFL 書体が PPTX に実際に埋め込まれているか(PowerPoint COM 実機レンダで書体名を目視確認)。
10. 新規画像生成の前に、同一案件の既存アセットを確認した記録(sha256 突合・ファイル一覧 grep)があるか。
