# オペレーターの判断原則

このファイルは「オペレーターがどの成果物を通し、どれを却下するか」の癖を原則化したもの。
賢いモデルは毎月出るが、この蓄積だけは誰にも出荷できない——この環境で最も価値のあるファイル。

## 運用ルール

- 原則の追加は distill-rejections スキル経由でのみ行う(オペレーター承認済みのものだけ)。
  例外は下記「初期原則」: 旧環境(multi-agent-crew)で既に裁定済みの規律を汎用化して移植したもの。
- 原則は**汎用化して書く**。固有名詞(顧客名・案件名・店舗名)を含めてはならない
  (このスキルは git 共有されるため)。
- 矛盾する原則ができたら、新しい方を残して古い方に取り消し線を引き、日付を添える。
- 形式: 「(場面)では(こうする/こうしない)」を1行。必要なら理由を1行添える。

## 原則

### 初期原則(旧環境の裁定から移植・2026-08-28)

**完了判定・検証**
1. テスト報告で SKIP が1件でもあれば「未完了」。SKIP=FAIL。「完了」と報告しない。
2. 状態確認は現物(実ファイルの mtime/内容・実DB・実環境の応答)で行う。ファイル名に埋め込まれた
   時刻や他クルーの PASS 宣言を転記しない。転記に留まるときは「文書X(日時)による・実地未確認」と明記する。
3. UI/フロントの動作確認は実ブラウザでの実クリック・実入力を伴う E2E で行う。コード読解や静的 DOM 検査
   だけで PASS と言わない。E2E ができない場合は代替検証の範囲と保証しない範囲を明記し、PASS と偽装しない。
4. 副作用(メール送信・外部API呼び出し)は呼び出し元の成功表示(トースト・HTTP 200)ではなく、
   発生先(送信ログ・受信側)で独立に裏取りしてから「実行済み」と報告する。ダミートランスポート設定を先に確認する。
5. 開発/検証環境への反映完了は、対象ディレクトリ全量の sha256 突合で MISMATCH 0 件を確認してから報告する。
   ファイルの存在確認だけでは完了の証跡にならない。
6. git commit を報告する前に `git cat-file -t` で実在、`git merge-base --is-ancestor <hash> HEAD` で到達性を
   確認する。hash は40桁で報告し、リポジトリを跨ぐ場合はリポジトリ名を併記する。
7. 件数・ステータスの集計では、同じ「成功」表示の中に意味の異なる分岐が無いかソースで確認する。
   「0件」はデータソースが対象範囲(保持期間・ローテーション・フィルタ)を覆っていると確認するまで「事象なし」の証拠にしない。
8. モデルや仲介ツール(WebFetch 要約等)の出力は証言であり観測ではない。重要な値は「一字一句引用・補完禁止」で
   再取得し、原文にない補完を結論から除外する。証拠が取れない値を「無い」「未反映」と結論しない。

**開発の進め方**
9. 開発系タスクは**モックファースト**: 操作できる UI モック → オペレーターの承認 → 仕様書の確定 → 本番実装の順。
   モック承認前の本番実装は禁止。モックで未確定の事項は「仮」と明示する。
10. 30件超の大量処理は、まず1件(または小バッチ)だけ実行して検品を通してから残りへ進む。
    誤った手法を全バッチで繰り返さない。
11. テストデータは実在レコードの丸コピーや部分書き換えで作らない。フィールド単位で明示的に構築し、
    連絡先には実在しない値、通知の引き金となるフラグは明示的に OFF を入れる。
12. 手順書・操作ガイドを書くときは、各ステップを実装(呼ばれる関数・エンドポイント)と実読で照合する。
    書きながら見つけた実装の不整合は独立したバグとして報告する。

**判断・報告**
13. オペレーターの判断が必要な事項は、報告の冒頭に 🚨要対応 としてまとめる。散らさない。忘れない。
14. 可逆・低リスクの判断は安全既定値で先行して後追い確認、不可逆・高リスク・純粋な好みの判断だけ止めて聞く。
15. 批判だけで止まらない。前提の矛盾は根拠つきで指摘し、代替案を出し、判断不能でない限り前進する。
16. 規律・仕様を変えたら、それが書かれている層(規約・手順・ダッシュボード・スクリプト)を同時に更新する。
    1箇所だけ直すと古い文言が「正しいもの」として残る。
17. 文書には「時点」を書く。コードは動かせば古いと分かるが、文書は読んでも古いと分からない。
18. 「在るのに効いていない」を疑う: 門(出口を見ていない)・配線(呼ばれていない)・テスト(誰も走らせない)・
    文書(走らないと書いてある)。直し方は共通で「出口を数える形にする」。

**秘匿・安全**
19. 秘密の生値を stdout・ログ・会話に出さない。第一防御は「出すコマンドを打たないこと」で、マスキングは保険。
20. 削除・kill・sudo・force push・プロジェクト外への書き込みは、必要だと思った時点で止まって報告する。

### 蒸留で昇格した原則

**再現系の制作(2026-09-09、オペレーターの直接裁定により追加)**
21. 「完コピ」「これと似たものを」と言われた制作では、参考(素)動画から取り出せるものを全て取り出して寄せる:
    フォント・BGM・アイコン・イラスト(フレーム切り出し+焼き込み字幕の除去)・効果音(音源分離で声を抜いて「何の音か・位置・音量」を特定し、実物は効果音ラボ等の無料素材から同じ音を選ぶ。参考の音声そのものは使わない)・
    レイアウト・時計(字幕切替とカットの実測時刻)。近い代替素材や似た系統の音で先に組まない。独自性は減点。
    理由: 評価軸は参考との一致度のみ。妥協してよいのは、参考から取り出せないもの(合成音声など)だけ。
22. 再現系で参考から取り出せないものは、着手前に「取り出せない理由」と「代替案」を1行で示し、判断を仰ぐ。
    近似で作ってから検品ループを回さない(工数と信用を失う)。

**動画の合格線(2026-09-11、オペレーターの直接指示により追加)**
23. 動画(short・長尺・切り抜き)の合格線は「オペレーターが提示した参考チャンネルの動画と並べて遜色ないこと」。
    機械検査 PASS・矛盾なし・破綻なしは最低条件であって合格ではない。設計は参考群の型と実測値(video-editing-reference)から始め、
    納品検品は同ジャンルの上位動画 2〜3 本の実フレームと並べて、テンポ・効果音の密度・テロップの密度と大きさ・画面の情報量・
    画面構成・サムネを比較し、見劣りする項目があれば REJECT にする(WARN に落とさない)。
    理由: 目的は公開して実績にすること。参考群に見劣りする動画は破綻が無くても価値が無い(「全然だめ。勉強したこと活かせてる?」)。
